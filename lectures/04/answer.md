### 1. 読んだ問題の要約と考察（Dataset Viewerより3件）

#### ① astropy__astropy-12907（天文学ライブラリの計算バグ）
- **問題文（症状）：** モデルを入れ子（ネスト）にして分離可能性行列（`separability_matrix`）を計算すると、独立しているはずの値が誤って計算される。なお、問題文に「どのファイルの何行目が原因か」は一切書かれていない。
- **自分なら解けるか：** 【絶対に解けない】天文学の専門知識もライブラリの構造も分からないため、コードのどこを触ればいいか見当もつかない。
- **正解の修正（答え）：** `astropy/modeling/separable.py` 内の `_cstack` 関数にある行列結合処理のたった1行を書き換える。
  ```python
  - cright[-right.shape[0]:, -right.shape[1]:] = 1
  + cright[-right.shape[0]:, -right.shape[1]:] = right
  ```
- **比較してわかる難しさ：** 答えは `1` を `right` に変えるだけの1行の修正だが、数千ファイルある巨大なライブラリの中から「行列計算のネスト処理をしている、原因の1行」をLLMが自力で探し出さなければならない点が極めて難易度が高い。

#### ② django__django-13089（Webフレームワークのキャッシュ削除バグ）
- **問題文（症状）：** データベースを使ったキャッシュの古いデータ削除時（`_cull`）に、データが空だと `NoneType` エラー（`cursor.fetchone()[0]` でのアクセス失敗）が発生する。
- **自分なら解けるか：** 【絶対に解けない】エラーが起きる原因は書いてあるが、ツールの内部構造を知らないため、どう書き換えれば正しく修正できるか分からない。
- **正解の修正（答え）：** `django/core/cache/backends/db.py` にて、いきなり `[0]` で取り出さず、データが存在するか確認する `if` 文を1つ追加する。
  ```python
  - cursor.execute("DELETE FROM %s WHERE cache_key < %%s" % table, [cursor.fetchone()[0]])
  + last_cache_key = cursor.fetchone()
  + if last_cache_key:
  +     cursor.execute('DELETE FROM %s WHERE cache_key < %%s' % table, [last_cache_key[0]])
  ```
- **比較してわかる難しさ：** 修正自体はシンプルな条件分岐の追加だが、この変更を加えたことで、キャッシュ全体の動作（200個以上ある既存テスト）に絶対に悪影響が出ないことを保証しなければならない点が難しい。

#### ③ sphinx-doc__sphinx-8459（ドキュメント生成ツールの表示バグ）
- **問題文（症状）：** `autodoc_typehints = 'description'` に設定すると、独自に定義した型エイリアス（`JSONObject` など）が機能せず、元の長い型名で表示されてしまう。
- **自分なら解けるか：** 【絶対に解けない】ツールの設定や内部の仕組みの知識が全くないため、お手上げである。
- **正解の修正（答え）：** `sphinx/ext/autodoc/typehints.py` にて、型情報を読み取る関数（`inspect.signature`）を呼び出す際、設定値を渡す引数を1つ追加する。
  ```python
  - sig = inspect.signature(obj)
  + sig = inspect.signature(obj, type_aliases=app.config.autodoc_type_aliases)
  ```
- **比較してわかる難しさ：** 答えは引数を1つ足すだけだが、「設定ファイルに書かれた `app.config.autodoc_type_aliases` という変数が、どのファイルのどの関数まで引き回されているか」というプロジェクト全体の設計ルールやデータフローを的確に読み取る必要がある。

### 2. 分析：LLMが解くとしたら何が難しいか（仕組み上の弱点）

1. **コンテキスト（一度に読める記憶容量）の限界**
   - **弱点と難しさ：** LLMは一度に処理できる文字数（トークン数）に上限があり、コードベース全体を丸ごと頭に入れると「真ん中の情報を見落とす」など精度が落ちる。`astropy` や `django` のような巨大プロジェクトは一度に全部読み込めないため、LLM自身が「どのファイルを開くべきか」を検索ツールを駆使して自力で絞り込む必要がある。
2. **「テスト（採点基準）」が見えない状態での推測**
   - **弱点と難しさ：** 通常の対話なら「こう直して」と指示されるが、SWE-benchでは合格条件である単体テスト（`FAIL_TO_PASS`）をLLMに見せないルールになっている。問題文（バグ報告）の自然言語だけを読んで、「開発者がどんな入力パターンでテストして、どんな出力を正解とみなしているか」を完全に自力で想像してコードを書く必要がある。
3. **暗暗の「設計ルール・お作法」の把握**
   - **弱点と難しさ：** LLMは一般的なPythonの文法は得意だが、そのプロジェクト独自の変数名や設計思想までは事前知識として持っていない。3件目の問題のように、他のファイルを読み込んで「このプロジェクトでは設定値をどうやって別の関数へ受け渡しているか」という独自ルールを正しく理解して追跡しなければ、正しい引数を追加できない。
4. **副作用（デグレード）の予測の難しさ**
   - **弱点と難しさ：** LLMは「目の前のエラーを消すコード」を局所的に生成するのは得意だが、その変更がプログラム全体の別の場所にどう影響するかをシミュレーションするのは苦手である。2件目の問題のように、キャッシュ機能を少し書き換えた結果、一見無関係な別のキャッシュ処理など、200個以上ある既存テスト（`PASS_TO_PASS`）のどこか1つでも落とせば即不正解（0点）になる厳しさがある。
