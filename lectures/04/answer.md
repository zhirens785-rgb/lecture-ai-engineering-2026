  - **実際の問題例（Hugging Faceのデータセットから3件確認）**：
    1. **astropy__astropy-12907（複合モデルの依存関係を正しく計算できない問題）**
       - **問題の内容**：AstropyというPythonの天文学向けライブラリで、複数のモデルを組み合わせた場合に、`separability_matrix` が各出力と入力の依存関係を正しく計算できない問題。特に、複合モデルの中にさらに複合モデルが含まれるような入れ子構造で、依存関係の計算結果が誤っていた。
       - **修正内容**：`astropy/modeling/separable.py` の `_cstack` 関数を修正し、右側のモデルの依存関係情報を正しく反映するようにしている。また、入れ子になった複合モデルでも正しく計算できることを確認するテストが追加されている。
       - **自分なら解けるか**：現時点の知識では難しいと思う。Astropyの内部構造やモデル同士の依存関係、十分に理解できていないため、問題の原因を特定することが難しいと感じた。
       - **LLMにとって難しい点**：
         1. 複数のモデルを組み合わせた場合の内部的な処理を理解する必要があること。
         2. 入れ子構造になったモデルの依存関係を追跡し、どの段階で計算結果が誤るのかを特定する必要があること。
         3. 修正によって通常のモデルや別の組み合わせの計算に悪影響が出ないことを確認する必要があること。
    2. **django__django-13109（ForeignKeyの検証で不適切なManagerが使われる問題）**
       - **問題の内容**：Djangoで、`ForeignKey` が参照先のデータを検証するときに、適切ではないManagerが使われる問題。アーカイブ済みのデータを通常の検索対象から除外するように設定している場合、データ自体はデータベースに存在しているにもかかわらず、フォームから登録しようとすると「指定されたIDのデータが存在しない」というエラーになることがある。
       - **原因と修正内容**：フォーム側では `_base_manager` を使っている一方、`ForeignKey.validate()` では通常の検索条件に左右される `_default_manager` を使っていたため、アーカイブ済みデータを見つけられなくなっていた。`django/db/models/fields/related.py` の `ForeignKey.validate()` で使うManagerを `_base_manager` に変更し、関連テストが追加されている。
       - **自分なら解けるか**：現時点の知識では難しいと思う。DjangoのManagerの仕組みや、`_default_manager` と `_base_manager` の違いを理解していないと、なぜデータが存在するのにエラーになるのかを判断できないため。
       - **LLMにとって難しい点**：
         1. DjangoのManagerの仕組みや、それぞれの役割の違いを理解する必要があること。
         2. フォーム側の処理と `ForeignKey` の検証処理を追い、異なるManagerが使われていることを発見する必要があること。
         3. 単純にエラーを回避するだけでなく、アーカイブ済みのデータや通常のデータに対して、ほかの機能の動作を壊さない修正にする必要があること。
    3. **matplotlib__matplotlib-26208（2つのグラフを重ねた際にデータ範囲がおかしくなる問題）**
       - **問題の内容**：Matplotlibで `twinx()` を使って2つのグラフを重ね、特定の順番で `stackplot` と `plot` を実行すると、最初のグラフのデータ範囲が無限大（`inf` や `-inf`）に変わってしまう問題。2つ目のグラフを作成した際に、元のグラフの軸の情報が正しく引き継がれていなかったことが原因。
       - **修正内容**：`twinx()` で新しいグラフを作成するときに元のグラフのx軸の単位情報を引き継ぐように修正し、`twiny()` についても同様に元のグラフのy軸の単位情報を引き継ぐようにしている。
       - **自分なら解けるか**： Matplotlibの基本的な使い方やグラフの作成方法は理解しているが、今回の問題を自力で解決するのは難しいと思う。特に、twinx() で作成したグラフ同士の軸情報の引き継ぎや、単位情報が内部でどのように管理されているのかといった詳細までは理解できなかった。そのため、問題の再現はできても、原因となる処理を特定して適切に修正することは難しいと感じた。
       - **LLMにとって難しい点**：
         1. 複数の条件が重なったとき発生する不具合なので、再現条件を正確に理解する必要があること。
         2. 2つのグラフの間で、軸の情報がどのように共有・管理されているのかを調べる必要があること。
         3. 軸の情報を引き継ぐ修正によって、通常のグラフ表示やほかのグラフ機能に影響が出ていないか確認する必要があること。
- 結果：
  - **作成・検証方法**：
    - 確認作業には93人の経験豊富なPython開発者が参加した。まず50件の例題を使った選考・導入段階があり、その後、元のSWE-benchから選ばれた1,699件の問題を対象に、それぞれ3人の開発者が独立して確認した。
    - 確認では「Issueの明確さ（問題文を読んで何を修正すべきかが十分に理解できるか）」と「テストの妥当性（修正が正しいかどうかをテストで適切に判定できるか）」の2点が0〜3の4段階で評価され、深刻な問題があると判断されたものは除外された。その結果、元の問題の68.3%が除外され、最終的に500件がSWE-bench Verifiedとして選ばれた。
  - **評価方法**：
    - AIモデルが提出した修正パッチを適用し、以下の2種類のテストを実行することで問題を解決できたかどうかを判定する。
      - `FAIL_TO_PASS`：修正前には失敗していたが、正しい修正を適用すると成功するべきテスト（Issueで報告された問題が解決したかを確認）。
      - `PASS_TO_PASS`：修正前から成功していたテスト（修正によって、もともと正常だった機能が壊れていないかを確認）。
    - 最終的には、テストに合格して問題を解決できたタスクの割合（% Resolved）でモデルやエージェントの性能を比較する。ただし、テストで確認できる範囲には限界があるため、テストに合格したからといってあらゆる状況で完全に正しい修正であると保証されるわけではない。
